# 项目学习笔记

服务于一位有十年以上、以前端为主的软件开发经验的学习者：建立模型、数据、训练、评估与 GPU 知识，并形成能解释和复现的工程能力。

## 何时沉淀

- 讨论澄清了一个重要概念、误区或有用的技术取舍。
- 实践产生了可复用的排错方法、工具用法或实验认识。
- 用户明确要求记录或复习。

不要求每轮对话都产生笔记。确认操作、推送状态和没有可复用结论的闲聊不单独成篇。避免为了沉淀打断当前问题；把整理合并到本次任务完成前。

## 放在哪里

- `knowledge/README.md` 是稳定的复习入口，按主题组织阅读链接。
- 知识页使用稳定、可读的小写连字符文件名，例如 `knowledge/hardware/tflops.md`。允许按主题分目录，不预建空分类。
- 默认原地更新对应主题，由 Git 保存历史；只有比较版本本身有学习价值时才单独保留版本。
- 小型配图放在相关主题的 `assets/` 中，需要时再创建。
- 项目决策放在 `docs/decisions/`，完整实验过程放在 `docs/experiments/`，知识页只提炼可复用认识并互链。不要复制整份实验报告。
- `knowledge/archive/` 是旧方案迁移时保留的历史材料，不是当前知识来源，也不是每次更新必须写入的位置。

## 写作与更新

1. 从索引和相关主题查找已有内容，优先合并同一问题；只查当前相关范围。
2. 默认中文，保留必要英文术语。面向有经验的开发者解释新领域知识，贴近实际例子、代码和张量形状。
3. 根据内容选择组织方式：原始问题、核心解释、具体例子、常见误区、适用边界。可加入 1～3 个自测问题；不要强制每页套齐所有栏目。
4. 标明来源与未确定事项，区分通用知识、项目建议、文献结论、推断和亲自实测。讨论整理不是独立事实验证，建议不是能力保证。
5. 有实质修订时注明更新日期；不要求 YAML 元数据、独立维护日志或按时间复制文件。
6. 更新索引和必要互链。遇到旧结论冲突，解释修订理由，不把历史估计伪装成已验证事实。

工具笔记强调“解决什么问题、何时使用、如何判断有效”；排错笔记强调“症状、根因、验证方法”。不能用技术名词清单替代理解，也不把某个工具写成唯一正确选择。

## 完成与提交

检查新增或修改的链接与引用；涉及代码或性能结论时，核对对应的实际证据。纯文档工作不引入训练测试或大规模扫描。

提交与推送遵循根目录 `AGENTS.md` 的既有授权、提交格式与失败处理；本技能不单独扩大权限。若本次只是用户明确要求快速 `push`，直接按 Push 约定执行，不额外补笔记或做扫描。

回复用简短链接指出新增或更新内容，不复述整篇笔记。用户反馈笔记过细、过浅或难复习时，优先调整内容和组织方式。
